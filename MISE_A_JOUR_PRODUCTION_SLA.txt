================================================================
 MISE A JOUR PRODUCTION — Correctif performance "hors_sla"
 Date : 2026-07-28
================================================================

CONTEXTE
--------
Un test de montee en charge (k6, jusqu'a 25 utilisateurs simultanes) a
revele que GET /api/reclamations executait un UPDATE sur toute la table
"reclamations" a CHAQUE appel (mise a jour du flag hors_sla). Sous charge
concurrente, cela cree de la contention sur PostgreSQL et fait exploser
les temps de reponse (p95 passe de 1.15s a 3.59s entre 1 et 25 utilisateurs).

Correctif applique et valide en local :
  - Le UPDATE ne s'execute plus que si necessaire (verifie via un SELECT
    EXISTS leger avant).
  - L'index partiel idx_reclamations_sla est aligne sur le predicat exact
    utilise par le code (hors_sla = FALSE AND statut NOT IN ('resolu','rejete')).

Resultat mesure (meme test, 25 VUs) :
  - p95 latence      : 3.59s  ->  0.72s
  - Debit            : 8.8 req/s -> 28.6 req/s
  - Taux d'erreur     : 0% -> 0% (inchange)

FICHIERS MODIFIES
------------------
  - backend/src/Controllers/ReclamationController.php   (methode index())
  - backend/database/schema.sql                          (definition de l'index, pour les futures installations "from scratch")

Aucun changement de schema de donnees (colonnes/tables), aucune migration
de donnees necessaire. Uniquement : 1 fichier PHP + 1 index a recreer.

================================================================
ETAPE 1 — SAUVEGARDE (avant toute action)
================================================================
Toujours faire un dump de la base avant une intervention en production :

  pg_dump -h <HOTE_PG> -U <USER_PG> -d <NOM_BASE> -F c -f backup_avant_fix_sla_$(date +%Y%m%d).dump

================================================================
ETAPE 2 — MISE A JOUR DE L'INDEX (base PostgreSQL)
================================================================
A executer directement sur la base de production (psql, pgAdmin, ou autre
client SQL). Le mot-cle CONCURRENTLY evite de verrouiller la table en
ecriture pendant la recreation de l'index (important si l'appli est deja
utilisee en meme temps).

IMPORTANT : CONCURRENTLY ne peut pas s'executer a l'interieur d'une
transaction (pas de BEGIN/COMMIT autour). Executer chaque instruction
separement.

  DROP INDEX CONCURRENTLY IF EXISTS idx_reclamations_sla;

  CREATE INDEX CONCURRENTLY idx_reclamations_sla
      ON reclamations(date_echeance_sla)
      WHERE hors_sla = FALSE AND statut NOT IN ('resolu', 'rejete');

Verification (doit renvoyer une ligne avec le bon predicat) :

  SELECT indexname, indexdef FROM pg_indexes
  WHERE tablename = 'reclamations' AND indexname = 'idx_reclamations_sla';

================================================================
ETAPE 3 — DEPLOIEMENT DU CODE PHP
================================================================
Deployer la nouvelle version de :

  backend/src/Controllers/ReclamationController.php

Selon votre mode de deploiement habituel (Laragon : recopier le dossier
backend/ mis a jour, ou pull git puis redemarrer/recharger PHP-FPM /
Apache si necessaire). Aucun redemarrage de PostgreSQL n'est requis.

L'ordre entre l'etape 2 et l'etape 3 n'est pas critique : le nouveau code
fonctionne correctement meme si l'index n'est pas encore recree (il fait
simplement un scan un peu moins optimal en attendant), et l'ancien code
fonctionne toujours avec le nouvel index. On peut donc deployer les deux
etapes l'une apres l'autre sans coupure de service.

 MISE A JOUR PRODUCTION 4 — Pieces jointes : securite + fiabilite (P1 / CT008)
 Date : 2026-08-03
================================================================

CONTEXTE
--------
Le rapport de tests avait releve (CT008) l'absence de limite fiable de
taille/format pour les pieces jointes, et (CT010) le fait qu'une piece
jointe puisse etre "non consultable" par le Pilote.

En auditant le code, un bug plus grave que ce que decrivait le rapport a
ete identifie : le lien de telechargement/ouverture d'une piece jointe
etait CASSE POUR TOUT LE MONDE. Le frontend transmet le jeton
d'authentification en parametre d'URL (necessaire pour un lien <a href>
ouvert directement par le navigateur), mais le backend ne lisait le
jeton que dans l'en-tete HTTP Authorization — jamais dans l'URL. Chaque
clic sur "Telecharger" ou "Ouvrir" echouait donc systematiquement (401).
C'est tres probablement la cause exacte du constat CT010.

Deux failles de securite ont egalement ete corrigees au passage :
  - Le telechargement d'une piece jointe (download()) ne verifiait
    AUCUN droit d'acces : n'importe quel utilisateur connecte pouvait
    telecharger n'importe quel fichier en devinant son identifiant,
    meme hors de son agence.
  - La suppression d'une piece jointe (delete()) autorisait tout
    coordonnateur ou superviseur, de n'importe quelle agence, a
    supprimer n'importe quel fichier (pas de verification d'agence).

Correctifs appliques et valides :
  - Le jeton d'authentification est desormais egalement accepte en
    parametre d'URL (?token=...), en repli si l'en-tete est absent.
  - Le controle d'acces par agence (deja utilise pour la liste et
    l'ajout de fichiers) est desormais applique aussi au telechargement
    et a la suppression.
  - Limite de taille de 5 Mo par fichier, appliquee cote serveur, sur
    la saisie interne ET le portail public (le portail affichait deja
    "Max 5 Mo" sans que ce soit reellement applique).
  - Sur le portail public, un fichier rejete (format ou taille invalide)
    est desormais explicitement signale dans la reponse et affiche a
    l'usager, au lieu d'etre supprime silencieusement alors que la
    reclamation etait annoncee comme un succes total.
  - Cote saisie interne, les fichiers rejetes par le serveur (deja
    remontes par l'API mais ignores par l'interface) sont maintenant
    affiches a l'utilisateur.

Aucune migration de base de donnees necessaire pour cette mise a jour.

  - backend/src/Controllers/PublicController.php       (limite 5 Mo + remontee des fichiers rejetes dans la reponse)

Frontend :

 MISE A JOUR PRODUCTION 6 — Fiabilite face aux Service Workers perimes
 Date : 2026-08-10
================================================================

CONTEXTE
--------
Signale par un utilisateur : sur Firefox uniquement, connexion impossible
avec l'erreur "JSON.parse: unexpected end of data at line 1 column 1",
meme apres avoir vide le cache, les cookies et l'historique du navigateur.
Le probleme ne se produisait pas sur Chrome.

Cause identifiee : l'application est une PWA (vite-plugin-pwa). Un
Service Worker issu d'un test anterieur d'un build de production (npm
run build + npm run preview) etait reste enregistre sur l'origine
concernee dans le profil Firefox de l'utilisateur, et interceptait les
appels /api/* en renvoyant une reponse vide. Les Service Workers et le
"Cache Storage" associe sont geres a part par Firefox : les actions
standard "vider le cache", "vider les cookies" et "vider l'historique"
ne les suppriment PAS. Il faut passer par "Gerer les donnees" (Cookies
et donnees de sites) ou desinscrire le Service Worker manuellement.

Solution immediate donnee a l'utilisateur (cote navigateur, aucune
action serveur requise) :
  about:preferences#privacy -> Cookies et donnees de sites -> Gerer les

 NOTE CORRECTIVE (2026-08-11) — Cause reelle de l'erreur JSON.parse
================================================================

L'erreur "JSON.parse: unexpected end of data" a finalement ete
diagnostiquee avec certitude a partir d'une capture du terminal de
l'utilisateur. La cause n'etait PAS un Service Worker perime (la mise a
jour 6 reste utile en defense en profondeur, mais n'etait pas la cause).

CAUSE REELLE (environnement de developpement uniquement)
--------------------------------------------------------
L'utilisateur lancait DEUX serveurs frontend en meme temps :
  - le conteneur Docker "ereclamations_frontend" (port 5173), qui
    proxifie /api vers le backend via VITE_API_URL=http://nginx (OK) ;
  - un "npm run dev" lance directement sous Windows (meme port 5173),
    pour lequel VITE_API_URL n'est PAS defini. Le proxy Vite retombait
    alors sur sa valeur par defaut "http://localhost:81", or le backend
    (nginx) est expose sur l'hote au port 8888, pas 81.

Resultat : le "npm run dev" hote renvoyait ECONNREFUSED sur chaque appel
/api/* -> corps de reponse vide -> "JSON.parse: unexpected end of data".
Selon lequel des deux serveurs gagnait le port 5173, un navigateur
tombait sur le serveur qui marche (Docker) et l'autre sur celui qui
echoue (hote), d'ou l'incoherence Chrome vs Firefox.

CORRECTIF
---------
  - frontend/vite.config.js : valeur par defaut du proxy corrigee de
    "http://localhost:81" a "http://localhost:8888" (port reel de nginx
    sur l'hote). Le "npm run dev" hote atteint desormais le backend.

REGLE D'EXPLOITATION (dev)
--------------------------
Ne lancer QU'UN SEUL frontend a la fois :
  - soit le conteneur Docker (deja demarre par docker compose up) et on
    utilise http://localhost:5173 ;
  - soit "npm run dev" sous Windows APRES avoir arrete le conteneur
    frontend (docker compose stop frontend).

IMPACT PRODUCTION : AUCUN.
Le proxy Vite n'est utilise qu'en developpement (npm run dev). En
production, "npm run build" genere des fichiers statiques servis par le
serveur web (nginx/Apache) qui route lui-meme /api ; ce parametre
n'intervient pas. Ce correctif ameliore uniquement le confort de
developpement local.

 MISE A JOUR PRODUCTION 8 — Refonte des profils utilisateurs
 Date : 2026-08-11
================================================================

CONTEXTE
--------
Le role technique "coordonnateur" avait ete detourne : concu au depart
pour les coordonnateurs des structures centrales (suivi + analyse des
reclamations), il servait en pratique de "Manager de service/section
accueil reclamations" (cloture des tickets). Le vrai profil coordonnateur
etait donc perdu. Par ailleurs, le profil "administrateur" unique devait
etre scinde en deux : fonctionnel (referentiels metier) et systeme
(technique).

NOUVEAU MODELE (7 roles)
------------------------
  - agent                       : cree les reclamations (ses dossiers).
  - pilote                      : analyse, projet de reponse, soumet,
                                  escalade (perimetre agence).
  - coordonnateur  (RESTAURE)   : structure centrale, suit et ANALYSE les
                                  reclamations. Perimetre TRANSVERSE. Ne
                                  cloture PAS.
  - manager        (NOUVEAU)    : Manager de service/section accueil
                                  reclamations. CLOTURE, retourne a
                                  l'initiateur, saisit les "Observations
                                  du manager". Perimetre agence.
  - superviseur                 : supervision + reporting + workflow.
                                  Perimetre transverse. Conserve le
                                  parametrage metier.
  - administrateur_fonctionnel (NOUVEAU) : referentiels metier (motifs,
                                  causes, modes de saisine, regimes &
                                  clients, processus, affectations,
                                  objectifs SLA, base de connaissances,
                                  analytics, gestion des interims).
  - administrateur_systeme     (NOUVEAU) : technique (agences, personnel,
                                  comptes & roles, configuration mail,
                                  audit & logs, travailleurs / employeurs
                                  / sinistres).

BASCULE DES COMPTES EXISTANTS (automatique via la migration) :
  - coordonnateur  -> manager
  - administrateur -> administrateur_systeme (a reaffecter en
                      administrateur_fonctionnel au cas par cas ensuite).

POINTS D'ATTENTION (changements de comportement)
------------------------------------------------
  1. Le "super-admin" implicite a ete SUPPRIME : auparavant le role
     administrateur contournait TOUS les controles de role. Desormais
     chaque admin (fonctionnel / systeme) n'a que son perimetre explicite.
  2. Le Manager (ex-coordonnateur) N'A PLUS acces au parametrage ; il se
     recentre sur son workflow (cloture / renvoi / observations).
  3. Le Superviseur PERD le parametrage technique (agences, personnel,
     comptes) mais conserve le parametrage metier (referentiels).
  4. La creation/modification de comptes utilisateurs est desormais

  5. Bug latent corrige au passage : la route /api/interims utilisait

     utilisateur authentifie. Corrige en requireRole(['administrateur_systeme']).

 MISE A JOUR PRODUCTION 16 — Correctif reel : N° CNPS "exige" sur le portail public
 Date : 2026-08-29
================================================================

CONTEXTE
--------
Suite a la MAJ 15, l'utilisateur a confirme que le probleme persistait
SPECIFIQUEMENT sur le portail public (/declarer) : un travailleur salarie
ou independant declare "Non immatricule" recevait quand meme l'erreur
"Le Numero CNPS est obligatoire pour un travailleur immatricule." au
moment de l'envoi final.

CAUSE REELLE (differente de la MAJ 15, qui corrigeait un autre bug sur
la saisie interne) : le portail public envoie les donnees en
multipart/form-data (FormData, necessaire pour joindre des fichiers).
Le booleen JS `false` envoye via FormData.append() est automatiquement
converti en la CHAINE DE CARACTERES "false". Cote backend
(PublicController::submit()), la ligne :

    $estImmatricule = !array_key_exists(...) || (bool)$data['partenaire_immatricule'];

utilise un cast (bool) sur cette valeur. Or en PHP, (bool)"false" vaut
TRUE (seules "" et "0" sont considerees "fausses" par le cast bool d'une
chaine non vide) : le choix "Non" de l'utilisateur etait donc SYSTEMATI-
QUEMENT INVERSE en "Oui" cote serveur, d'ou l'exigence erronee du
Numero CNPS. Ce bug est invisible sur la saisie interne (agent) car
celle-ci envoie du JSON pur (booleens natifs preserves par json_decode).

Confirme par reproduction complete (navigateur + inspection de l'etat
React + test curl multipart direct) : avant correctif, un envoi
multipart avec partenaire_immatricule=false etait rejete a tort ; apres
correctif, la reclamation est creee avec succes et le flag est bien
enregistre a `false` en base.

CORRECTIF
---------
Interpretation explicite de la valeur, qu'elle soit un booleen natif
(chemin JSON) ou une chaine (chemin multipart/$_POST) : les chaines
"false", "0" et "" sont traitees comme false, toute autre valeur comme
true (comportement par defaut a true si le champ est absent, pour
retro-compatibilite).

FICHIERS MODIFIES
------------------
Backend :
  - backend/src/Controllers/PublicController.php  (methode submit() : derivation de $estImmatricule)

DEPLOIEMENT : backend uniquement (PHP), effet immediat. Aucune migration,
aucun changement frontend necessaire pour ce correctif specifique.

VERIFICATION POST-DEPLOIEMENT (portail public /declarer, formulaire
REEL avec pieces jointes ou non) :
  - Travailleur salarie ou independant + "Non immatricule" -> declaration
    envoyee avec succes, numero de ticket genere, AUCUNE erreur sur le
    Numero CNPS.
  - Travailleur salarie ou independant + "Oui immatricule" SANS numero
    -> toujours rejete avec le message attendu (regression testee, OK).
  - Verification en base : SELECT partenaire_immatricule FROM
    reclamations WHERE id = <id_du_test> ; doit valoir 'f' pour le cas
    "Non".
